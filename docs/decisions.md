# Decisions

Each entry: `## YYYY-MM-DD: decision`, then the reason, who decided, and what was rejected and why. Newest first.

## 2026-11-14: Floating buttons and settings.json: places per monitor, the grid next to the button
- Button: a dark rounded square, 32 px at 100 % scaling (48 px at 150 %), with a white ^ like Windows' hidden-icons arrow, lighter under the mouse, tooltip "Tray icons (Alt+`)". One per secondary monitor, first just above the right end of its taskbar; dragged within its monitor only; right-click: Exit. It doesn't take the keyboard focus when it appears, only when clicked or dragged. Reason: a button that never takes the focus has a known problem: its right-click menu may not close on a click elsewhere, like Steam's. Drawback: dragging it takes the focus from the window the user was typing in.
- ~~The grid on a monitor with a button opens next to it, by the hotkey too: right edges lined up, just above the button (below if there is no room above). A place the grid was dragged to wins.~~ Replaced after the owner's test: with the grid dragged away, the button's ^ pointed at nothing ("feels weird to click the up arrow and have the tray show up somewhere else").
- The button alone says where the grid is on its monitor: the grid always opens next to it, by the hotkey too, with right edges lined up: above the button, or below it when the button is in the top half of the monitor, and the arrow turns into a v then (one rule for both, so they agree). ~~A dragged grid stays where it is while open, but opens at the button again next time; dragging the button while the grid is open moves the grid along when the button is let go.~~ Replaced after the owner's next test ("when I drag the tray, the arrow doesn't move with it"): the button and the grid move together while either one is dragged. Dragging the grid brings the button along below it (right edges lined up), or above it where below would be in the top half of the monitor. At a monitor edge where the button has no room, the grid moves a little when let go, to make room. The button's place is saved either way. Only on a monitor without a button (the main one) does the grid open where it was last dragged. Reason: one handle per monitor; the button starts in the corner where the hotkey's grid used to open, so the grid would cover it otherwise. Drawback: the button can't stay in the corner with the grid in the middle; move the button instead. Rejected: the dragged place for the hotkey only (still two places per monitor); "below only if there's no room above" (depends on the grid's height, which the button can't know, so the arrow couldn't match). Changes "Placement" in "The grid app" below for the hotkey.
- A click on a button, or Alt+` with the mouse on another monitor than the open grid's, moves the grid there; on the same monitor it closes it. Changes the step A behaviour, where Alt+` on another monitor only closed the grid.
- settings.json holds the button's place per secondary monitor and the grid's dragged place on a monitor without a button, by Windows' name for the monitor (DISPLAY5) and measured from the monitor's top-left corner, so rearranging monitors keeps them. Each drag saves the file (written to a .tmp file, then moved over the old one). A file that can't be read: a message at start, the default places, and the file is never written over. Drawback: when Windows gives a monitor a new name (it can after re-plugging), its places are forgotten. Rejected: the monitor's hardware ID as the key (stable, but ~25 more lines of Win32 code; only if renaming happens).
- When monitors change (Windows' DisplaySettingsChanged: plugged in or out, resolution, arrangement), the buttons are made again and an open grid closes.
- Decided by: the owner (Claude's suggestions), To do 3 step C.

## 2026-11-14: A forwarded click lets any program come to the front
- `TrayClicks` calls `AllowSetForegroundWindow(ASFW_ANY)` before each left or right click. Reason: Steam showed its tray menu for a forwarded click only while Explorer was the program in front (owner's test, To do 3 step B; docs/research/uia-tray.md "Steam's menu didn't open"). The grid is in front when its tile is clicked, so it can pass the right on. Windows refuses the call when the caller isn't in front, so it does nothing then.
- Decided by: Claude, from that test (the owner had agreed to the fix if the test showed this cause).
- Rejected: allowing only the icon's program (its exe is a guess for icons matched by order, and Steam's menu belongs to a helper process, steamwebhelper, not steam.exe). Drawback: until the next key press or click, any program could come to the front, not only the clicked one.

## 2026-11-14: The grid app: Alt+`, dark, reads before it shows, stays on top until its X
- Hotkey Alt+` (Alt and the key left of 1), a constant in the code. First Ctrl+Alt+T; the owner found it awkward to press after testing step A and took Claude's suggestion: one hand, two neighbouring keys, free on this PC (RegisterHotKey succeeded, measured). Rejected: Ctrl+Space (VS Code's suggestions use it), Win+Y (keys far apart), Ctrl+Shift+Space (three keys), Insert/Pause/Scroll Lock (missing or behind Fn on laptops), a double tap of Ctrl (needs a keyboard hook that sees every key, ~40 lines); Win+` and the Copilot key are taken by Windows (measured). Also rejected: a setting for the hotkey now (a second place to look, for one user); it moves to the settings file only if it ever clashes.
- Content: app icons only, in "Pinned" (taskbar) and "Overflow"; no system icons (network, volume, clock: Windows gives secondary taskbars a clock). Tooltip text on hover only, to keep the grid small; an icon with an empty name shows its program's file name.
- Placement: opened by the hotkey, at the bottom-right of the work area of the monitor the mouse is on (where Windows' own flyout sits); opened by the floating button, next to the button. Once the user has dragged it on a monitor, it opens there on that monitor (kept while the app runs; saved in the settings file from step C). Changed in step C: on a monitor with a floating button the hotkey also opens it next to the button (see "Floating buttons and settings.json" above).
- Stays open, on top, until its X, Escape or the hotkey closes it; a click elsewhere or on an icon doesn't close it. Changed by the owner after testing step A (first: it closed on a click elsewhere and after a click on an icon). It has a small dark title bar of Windows' own (an X, and dragging it moves the grid) and stays on its monitor while dragged. Reason for the title bar: Windows gives the X and the dragging for a few lines of code. Rejected: a hand-drawn × in the grid's corner (more compact, but no dragging without ~30 more lines). Reason for keeping it on its monitor: on a monitor with other scaling it would have to be laid out again, which ran into WinForms resizing its fonts (docs/research/winforms-dpi.md). Known drawback: it covers what is under it, including the owner's Session Inbox popups, which sit in the same corner.
- Refresh while open stays at every 2 s, even though the grid can now stay open all day: a full read took about 120 to 150 ms (measured), about 6 to 7 % of one CPU thread, about 0.2 % of this PC's 32 threads (estimated). To be measured in step B; slower while unused only if it shows. Measured in step B (one 60 s run of the same reads every 2 s, in a probe): the reading program used 6.6 % of one thread, Explorer 12.6 % against 4.6 % and 7.6 % in the minute before and after, so about 6 % more (estimated from that difference; Explorer's own load varies). Together about 13 % of one thread, about 0.4 % of the PC's 32 threads, while the grid is open. The owner (after testing step B, Claude's suggestion): keep 2 s for now; reading less often while the grid isn't used is To do 8 (Someday).
- Look: dark, rounded corners, icons at the tray's own size (16 px at 100 % scaling) in 40 px tiles, up to 6 per row. Reason: the taskbar icon pictures are cut from the taskbar with its dark background (RGB about 34, measured on 3 pictures), so a dark grid hides their square; 16 px at 150 % is 24 px, the size of those pictures, so they show 1:1. Rejected: following Windows' light theme (the owner uses dark; light would show the taskbar pictures as dark squares anyway).
- Opening: read the tray, then show the grid (about 0.15 s later, estimated from the ~150 ms full read measured in To do 2), so it never shows stale icons. Rejected: showing the last list at once and updating it (icons can jump under the mouse).
- ~~After a left or right click the grid closes, like Windows' own flyout.~~ Replaced (owner, after testing step A): the grid stays open after a click (see "Stays open" above); Steam's menu, which doesn't take the focus, then opens next to it.
- One copy at a time (a named mutex); one tray read at start (warms up UI Automation, and any one-off flyout flash happens then). Exit is in the floating button's right-click menu (owner). Claude added the same Exit to a right-click on the grid's background (To do 3 step A), because step A has no button and the laptop alone has no secondary monitor, so no button.
- Floating button: one per secondary monitor, starting just above the right end of its taskbar, draggable. Known drawback: it is always on top, so it covers the corner of the windows under it and shows over full-screen video on that monitor; a Someday to-do if it bothers the owner.
- Decided by: the owner (Claude's suggestions), To do 3 planning. Built in 3 steps instead of the to-do's 5 (the plain text list of the old step A would be thrown away; clicks and refresh are both small).

## 2026-11-14: Clicks act on the tray button: Invoke for a left click, COM UI Automation's ShowContextMenu for a right click
- Reason: both work on the button itself, so the mouse doesn't move and overflow icons are clicked while the flyout stays closed. Measured with OneDrive, Steam and Discord: Invoke opened Discord's window, ShowContextMenu opened Discord's menu, both on a hidden overflow icon (docs/research/uia-tray.md "Spike step D"). ShowContextMenu isn't in .NET's UI Automation library, so src/Tray/TrayClicks.cs declares the few COM UI Automation methods it needs by hand and calls ShowContextMenu by its place in the interface's method table (about 60 lines of code).
- Decided by: Claude from the probes, following the owner's go-ahead for the to-do's plan (ShowContextMenu first, a simulated click only if it failed).
- Rejected: a simulated right-click on the real icon (moves the mouse to the main monitor and back, needs the icon on screen so the overflow flyout would have to open for every click, and the click lands in a full-screen window that covers the taskbar); opening the flyout for overflow clicks (not needed: hidden buttons take both clicks).
- Where the app's menu or window appears is the app's choice: at the mouse for Steam and Discord, above its icon on the main taskbar for OneDrive.

## 2026-11-14: Icon pictures: drawn live for taskbar icons; Windows' stored snapshot, matched by name then order, for overflow icons
- Reason: nothing links a tray icon to its program (Windows' undocumented ITrayNotify, UI Automation and the old Win32 tray all failed, measured). Windows' list of tray icons (NotifyIconSettings) has each program, a snapshot picture and an order that matched the overflow 12 of 12. Matching by name first, then by order for the icons in between, found 13 of 14 app icons, none wrong (measured once; docs/research/uia-tray.md "Spike step C"). Taskbar icons are drawn from the taskbar itself with PrintWindow: the live picture, also under a full-screen window. That fixes two icons that share one entry (two PowerShell scripts) and shows status changes, for about 50 to 75 ms more per read.
- Decided by: the owner (Claude's suggestions), To do 2 step C.
- Rejected: a generic picture whenever the name gives no match (about half the overflow would be generic, and icons with no name couldn't be told apart); the exe's own icon (wrong for Windows' icons and for scripts); opening the flyout to draw the overflow icons (a flash at every read).
- Moves the taskbar part of "Live tray icon pictures" out of Later; overflow icons stay snapshots, which can be older than the real icon.

## 2026-11-14: Read the overflow from its hidden window; refresh it with the visible icons every 2 s
- Reason: the overflow flyout's window exists while closed, and its buttons can be read through UI Automation from the window handle without opening it: no flicker, 16 to 28 ms per read. Its list followed added and removed icons and tooltip changes within a fraction of a second while the flyout stayed closed (measured with a test icon; docs/research/uia-tray.md "Spike step B"). So the reason for reading the overflow only on opening (the flyout would flash) is gone. Replaces the refresh part of "Grid opens by hotkey and floating button..." below.
- Decided by: the owner (Claude's suggestion), To do 2 step B.
- Rejected: opening the flyout to read it (visible flicker, slower); turning every icon on in Settings so nothing is in the overflow (changes the owner's settings and loses the Pinned/Overflow split); still reading the overflow only on opening (the cost is ~20 ms per refresh, and the grid would show stale overflow icons).
- After an Explorer start the window doesn't exist until the flyout has been opened once (owner's test, then a probe). So when it is missing, the code opens and closes the flyout once by invoking the arrow (`ReadOverflowItems(openIfMissing: true)`): a flash of about 0.2 s, and the keyboard focus moves to the taskbar (giving it back from another program failed, measured). It happens once per Explorer start (sign-in, Explorer restart). Callers that read every few seconds pass false, so a failure can't make the flyout flash every 2 s. The arrow is found by its name "Show Hidden Icons" (English Windows only): nothing else tells it apart.
- Fallback decided by: the owner (Claude's suggestion). Rejected: telling the owner to open the arrow once after each sign-in (no flash, but a manual step every day); turning every icon on in Settings (loses the Pinned/Overflow split).

## 2026-11-14: Find the taskbar window with Win32 FindWindow, then use UI Automation
- Reason: asking UI Automation to search the desktop's top-level windows for `Shell_TrayWnd` took 97 to 371 ms per read (35 windows open); `FindWindow` + `AutomationElement.FromHandle` took 1 to 5 ms (measured, details in docs/research/uia-tray.md "Spike step A"). A warm read of the tray dropped from ~130 ms to ~20 to 30 ms, which matters for the 2 s refresh. Win32 P/Invoke is allowed by the no-third-party rule.
- Decided by: Claude during To do 2, step A, from the measurement; the owner can overrule.
- Rejected: UI Automation only (`RootElement.FindFirst`): one fewer concept to read, but 4 to 10 times slower per read.

## 2026-11-14: One solution; the tray code in its own library
- Reason: the dump tool (To do 2) and the app (To do 3) both need the tray-reading code; a class library is the standard way to share it, and it keeps the code a Windows update may break in one place. One TrayAnywhere.slnx at the root, so a plain `dotnet build` builds everything; shared settings (net10.0-windows, nullable on, warnings as errors) in Directory.Build.props.
- Decided by: the owner (Claude's suggestion).
- Rejected: one project for everything (the dump is a console program and the app a windowed one; a windowed exe needs extra code to print to the terminal); linking the same source files into both projects (less standard, and easy to miss a file).

## 2026-11-14: Implicit usings off; a short hand-written .editorconfig
- Reason: with implicit usings off, every file lists the namespaces it uses, so a reader sees where names come from. The .editorconfig (~20 lines) sets indentation, System usings first, file-scoped namespaces and braces always; `dotnet format --verify-no-changes` fails on each of these (tested with a probe file).
- Decided by: the owner (Claude's suggestion).
- Rejected: implicit usings on (fewer lines, but names appear from nowhere); `dotnet new editorconfig` (389 lines of defaults, measured, that nobody would read).

## 2026-11-14: Checks are dotnet build (warnings as errors) and dotnet format; no unit tests at first
- Reason: the tray reading depends on the live taskbar, so a unit test would mostly test a fake. The tray dump (To do 2) is the real test; a GUI test comes with To do 4.
- Decided by: the owner (Claude's suggestion).
- Rejected: a unit-test project from the start (little to test without the real taskbar).

## 2026-11-14: Settings file in AppData; autostart via the Run registry key
- Reason: `$env:APPDATA\tray-anywhere\settings.json` (System.Text.Json, ships with .NET) is the usual place for per-user settings. The per-user Run key (HKCU\Software\Microsoft\Windows\CurrentVersion\Run) is the standard autostart, needs no admin and is one registry value.
- Decided by: the owner (Claude's suggestion).
- Rejected: settings next to the exe (breaks when the build output is cleaned); a Startup-folder shortcut (creating a .lnk needs COM code, more lines than one registry value).

## 2026-11-14: Grid opens by hotkey and floating button, on the mouse's monitor; overflow read only on opening
- Reason: the hotkey is for the keyboard, the button for mouse-only use. "The monitor the mouse is on" works for both external monitors without a setting. Reading the overflow means opening its flyout, so polling it every 1-2 s would flash the flyout all the time; visible icons are cheap to read (the whole primary taskbar took ~0.5 s from PowerShell, measured), so they are re-read every 2 s while the grid is open.
- Decided by: the owner (Claude's suggestions).
- Rejected: polling everything every 1-2 s (flyout flicker); a fixed monitor in settings (needs a setting, and there are two external monitors).
- Revisit after To do 2 if the overflow can't be read without visible flicker. Alternative then: turn every icon on in Settings > Personalization > Taskbar > Other system tray icons, so nothing is in the overflow.
- Refresh part replaced (2026-11-14, To do 2 step B): the overflow can be read without opening the flyout, so it is re-read with the visible icons every 2 s. See "Read the overflow from its hidden window" above. The hotkey, button and monitor parts stand.

## 2026-11-14: C# on .NET 10 with WinForms, no NuGet packages
- Reason: the owner's rule is "only what ships with Windows or .NET". C# on .NET 10 gives modern C#, standard tools (dotnet build, dotnet format) and good VS Code support. WinForms keeps everything in C#, no XAML. .NET 10 is the long-term-support release; .NET 8 support ended in November 2026.
- Decided by: the owner (Claude's suggestion).
- Rejected: PowerShell (slow start, clunky window code, P/Invoke needs embedded C# anyway); the C# 5 compiler that ships with .NET Framework in Windows (nothing to install, but 2012-era C# and weak editor support); WPF (XAML is a second language to read); .NET 11 (just released, no gain for this app).
