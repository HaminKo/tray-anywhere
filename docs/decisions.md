# Decisions

Each entry: `## YYYY-MM-DD: decision`, then the reason, who decided, and what was rejected and why. Newest first.

## 2026-11-19: Drag to reorder: the grid's own order per section, kept by the program's file name
- What: a tile dragged in the grid takes the place under its centre; the other tiles of its section make room as it passes, and the release doesn't click the icon. Only within its section: a tile dropped over the other section goes to the nearest place in its own. The order is saved in settings.json as a list of keys per section (`PinnedOrder`, `OverflowOrder`), and each read is sorted by it: known icons in the saved order, new ones after them in tray order. Saved keys of icons not there during a drag keep their old places in the list, so a closed program gets its place back. "Reset icon order" in the right-click menu (buttons and grid) empties both lists.
- Key: the program's file name (`steam.exe`), else the icon's name. Measured on the owner's tray: 15 of 16 app icons have a program; 3 have no name, so a name alone can't be the key. The one without a program ("Session Inbox") changes its tooltip, so it counts as new (end of its section) after a change until dragged again: accepted. One program's two icons share a key and keep Windows' order between them: accepted (none today).
- Reason: the owner wants the order they choose in the grid, across refreshes and restarts.
- Decided by: the owner (Claude's suggestions), To do 14.
- Rejected:
  - Changing Windows' own order (`UIOrderList` in the registry): undocumented, and it would change the owner's taskbar.
  - Moving an icon between Pinned and Overflow by dragging: that writes Windows' settings, and Windows' taskbar settings page does it already.
  - The full program path as key: apps that update themselves into a new folder (Discord's `app-1.0.x`) would lose their place at each update.
  - WinForms' DoDragDrop (OLE drag and drop): it runs its own loop on the real mouse, so the GUI test couldn't drive it with messages; a drag within one window needs none of it.
  - No movement until the drop: cheaper by about 15 lines, but the user can't see where the tile will land.

## 2026-11-18: Windows' notification popups move to the mouse's secondary monitor: a mover only for the shell's toast window
- What: the app finds the shell's one toast window (class `Windows.UI.Core.CoreWindow`, title "New notification", process ShellExperienceHost) and hooks that process's "moved" events (out of context, as SteamMenu). While it shows a toast, the app keeps it (moves, no resize) at the bottom right of the free area of the mouse's monitor, further left by the scales' ratio, and corrects every later move; on the main monitor that is the shell's own place. First it moved the window only off the main monitor and then left it alone, but the shell sometimes moved it again, below the screen (owner's test). Every app's toasts and tray balloons: one window shows them all. Always on, no setting. This widens the 2026-11-16 Steam-only mover: a second mover, for this one window only.
- Reason: Windows shows toasts on the main monitor only. Measured (docs/research/notifications.md): the window can be moved from another process, stays and draws at the new monitor's scale; the shell moves it back for each new toast, and the hook reports each move. The filter is exact (class, title, process), unlike "any program's menu", rejected on 2026-11-16 for want of one.
- Decided by: the owner (Claude's suggestions), To do 13.
- Open: while a full-screen program covers the main monitor, Windows shows no toast at all (Do Not Disturb), so nothing moves. The owner tries Windows' switch "When using an app in full-screen mode" by hand; the app changes no Windows setting.
- Rejected:
  - A copy of each toast in tray-anywhere, read with UserNotificationListener (works during Do Not Disturb, and allowed for an unpackaged program, measured): .NET 10 needs Microsoft's Windows SDK projection (a NuGet download, against the no-NuGet rule) or hand-written COM interop for WinRT; and a copy's buttons wouldn't work.
  - Reading the toast's text with UI Automation for a copy: only while the toast shows, so not during Do Not Disturb, the case a copy would be for.
  - Only tray apps' toasts: a mover can't choose, one window shows them all.
  - Resizing the window to the new monitor's scale: the shell doesn't lay the toast out again, so it is cut off (measured).
  - A hook on every program's "moved" events: it would also get every move of the mouse pointer; the hook is for the shell's process only, found again every 5 s.

## 2026-11-18: Releases: a zip of the framework-dependent app on GitHub; no installer, not self-contained, not signed
- Reason: the app needs no install step (settings in AppData, Start with Windows from its menu, runs from any folder), so unzip-and-run is enough. The zip holds what `dotnet publish` makes: 7 files, 136 KB zipped (measured). Visitors install the .NET 10 Desktop Runtime once with winget. The version is in TrayAnywhere.csproj (0.1.0 first) and names the zip and the tag. The zip is built in `release/` (gitignored), since `publish/` is locked while the everyday copy runs. Steps: docs/releasing.md; measurements and sources: docs/research/release.md.
- Decided by: the owner (Claude's suggestions), To do 15.
- Rejected:
  - Installer builders (WiX, Inno Setup, NSIS): third-party software. MSIX: needs the Windows SDK's tools and a certificate that visitors' PCs trust.
  - Both a zip and an install script (the owner asked "why not both?"): the script would only copy the folder and add a Start menu shortcut, a downloaded .ps1 opens in Notepad on double-click, and it is a second install way to document and test. Revisit if visitors ask for one.
  - Self-contained (the owner asked "why not?"): can't be built on this PC, because any publish for `win-x64` (also single-file) needs Microsoft's runtime packs from nuget.org and the NuGet config has no sources (NU1100); about 175 MB unzipped (estimated), WinForms can't be trimmed, and its own copy of the runtime gets no security fixes without a new release.
  - Signing: a certificate costs money. The README says how to get past SmartScreen and names Smart App Control as a known limitation.
  - GitHub Actions building the release: more moving parts for a 4 s local publish.

## 2026-11-18: Overflow icons keep Windows' stored snapshot: no live picture (To do 12 closed as not possible)
- Reason: nothing gives the current picture of a hidden icon without opening the flyout (measured: docs/research/uia-tray.md "To do 12"). Windows writes the snapshot when it first sees a program's icon and didn't rewrite it after 12 picture changes, a flyout opening or a new start of the program. ITrayNotify sends nothing on this build. Explorer's overflow window, shown off-screen, draws plain black, because only Explorer's own opening lays out its content; cloaking it from another process is refused.
- Decided by: the owner, by the to-do's stop rule (Claude's suggestion), To do 12.
- Rejected: opening the flyout to draw it, also only once per grid opening (a flash, and the keyboard focus moves to the taskbar; the 2026-11-14 decision stands); making Explorer's window transparent (`WS_EX_LAYERED`) and showing it (changes Explorer's own window, and showing alone drew nothing); hooking `Shell_NotifyIcon` or reading Explorer's memory (code injected into Explorer); Windows.Graphics.Capture (needs a NuGet package, and the window draws nothing to capture).

## 2026-11-17: No overflow window and no arrow: nothing hidden (empty overflow), unless the "Hidden icon menu" switch is off (an error naming it)
- When the overflow window doesn't exist and the taskbar has no "Show Hidden Icons" arrow, the overflow reads as empty, without an error and without opening anything. If Settings' "Hidden icon menu" switch is off (registry `SystemTrayChevronVisibility` = 0), the read fails instead, with a message that names the switch. A window that exists is read as before, arrow or not; an arrow without a window is handled as before (opened once when the grid opens).
- Reason: with every icon on the taskbar Windows removes the arrow, and after an Explorer restart there is then no overflow window, so the read failed for a normal state. But the switch off also removes the arrow while the icons stay hidden, and after a restart those can't be read at all (no window, nothing to open it). The switch's value tells the two apart (measured: docs/research/uia-tray.md "To do 6"). An error is better than an empty Overflow there: otherwise the hidden icons vanish from the grid with no hint why.
- Decided by: the owner (Claude's suggestions), To do 6.
- Accepted downside: the arrow is found by its English name, so on a Windows in another language (or after an update that renames it) the overflow reads as empty after each Explorer start, without an error, until the flyout is opened once by hand.
- Rejected: "no arrow = nothing hidden" without the switch (wrong while it is off: 13 icons stayed hidden, measured); an empty list while the switch is off (hidden icons would vanish silently); turning the switch on for a moment from the app (writes the owner's settings, and the arrow would flash); a cross-check with Windows' tray list (`Shell_NotifyIconGetRect` gave false "no"s for 2 of 16 icons in To do 9, and running programs without an icon have entries too, so it can't prove "nothing hidden" either way).

## 2026-11-16: Icons matched by order use only programs Explorer shows an icon for, when there are extra programs; else no program
- Between two icons matched by name, unnamed icons take the running programs' entries in order. When there are more such entries than icons, the app asks Explorer (`Shell_NotifyIconGetRect`, documented) which of them have an icon now, keeps those, and pairs them in order if that leaves one per icon. If it doesn't, those icons get no program: the generic picture in the grid.
- Reason: a program that runs without a tray icon (VLC, measured) pushed Copilot's icon onto VLC's picture. Explorer's "yes" was right for every icon; its "no" was wrong for 2 of 16, whose program uses another icon number than Windows stored (Task Manager; a script that makes a new icon for each message). So it is asked only where extra entries exist, and name matches keep every entry. Costs about 20 to 50 ms more per read here (measured). Details: docs/research/uia-tray.md "To do 9".
- Decided by: the owner (Claude's suggestions), To do 9.
- Rejected: the best guess when the counts still don't add up (a wrong picture is worse than none; owner); dropping every entry Explorer says "no" to (Task Manager's icon would lose its match); a "shown now" value in Windows' stored list (there is none, measured); matching taskbar icons by the place Explorer gives (taskbar pictures are drawn live already; a possible Someday to-do).

## 2026-11-16: Steam's misplaced tray menu is moved to the click by a Steam-only mover on a WinEvent hook
- After a forwarded click, the app watches for Steam's tray menu (class `SDL_app`, title "Menu", process steamwebhelper) with out-of-context WinEvent hooks (shown, hidden, moved), set just before the click and removed 1 to 2 s after the last click, once no menu the app moves is open. Only a menu that opens within 1 s of the click is moved, until it hides. When it is far from the click, it is moved there with `SetWindowPos` (no activation, no z-order change): a corner at the click, opening up and to the right, flipped where there is no room, inside the monitor's free area. Every move Steam makes while the menu is open is corrected the same way.
- Reason: Steam's menu opens at mouse + monitor's top-left corner x (scale - 1), Steam's own bug (known on its forums since 2023); real clicks rarely meet it because the real tray is on the primary monitor at 0,0. Moving the menu keeps its hover and clicks working (owner's test). The hook corrects Steam's own moves within the same timer tick in most cases, so the flash at the wrong place is rare even when spamming clicks. Measurements: docs/research/uia-tray.md "To do 7 step A".
- Decided by: the owner (option C, "we might as well fix it now" for the flash), from Claude's options and the spike.
- Step B (owner, 2026-11-16, Claude's suggestions): the hooks don't go when the menu hides, as first planned: a second click on Steam's tile closes the open menu, and that "hidden" event can come in after the second click set its watch, which would leave the new menu unmoved. A menu that opens over 1 s after the last click (from Steam's real icon, say) isn't moved: found by the review, since hooks kept while a menu is open would otherwise move a menu reopened from the real icon to the grid. The GUI test's copy (`--gui-test`) also moves windows of the GUI test's own program, whose tray icon opens a window like Steam's menu far from the click; the test checks that it is moved. Rejected: matching by class and title only, with no switch (the everyday copy would also move the test's window and any other SDL program's "Menu" window).
- Rejected: Steam's setting "Scale text and icons to match monitor settings" off (fixes the place, but Steam no longer scales, so it is small on the 150 % monitors; owner); a mover for any program's menu (the owner's Session Inbox popups have the same window styles as menus and would be moved; no clean filter); checking every 15 ms (a flash at the wrong place at most spam clicks; owner's test); keeping the known limitation (owner); a hook inside Steam's process (needs a DLL injected into Steam: third-party code and a crash risk); reporting to Valve only (no timeline; the owner may still report it).

## 2026-11-15: Refresh every 2 s only while the mouse is over the grid, else every 10 s
- While the grid is open, a 0.5 s timer checks how old its icons are, and reads the tray again when they are older than 2 s with the mouse over the grid (title bar included), or older than 10 s otherwise (src/TrayAnywhere/App.cs `RefreshIfDue`, GridForm.cs `InUse`). So the mouse coming onto a grid left unused brings a read within about 0.5 s, plus the read itself. Replaces the 2 s refresh of "The grid app" below.
- Reason: the grid can stay open all day, and the 2 s refresh cost about 13 % of one thread while open (measured in To do 3 step B). Measured afterwards, same conditions, one run each: the app's CPU with the grid open and unused fell from 4.8 % to 2.2 % of one thread (a read after a 10 s pause costs about twice as much); Explorer's share couldn't be told apart from its own varying load, for either rate. Details: docs/research/uia-tray.md "To do 8: the slower refresh".
- Only the mouse counts as using the grid, not the grid being the window in front. Reason (raised by the code review): after Alt+` the grid is in front, and if the owner then leaves the PC it would stay in front and keep reading every 2 s. Drawback: right after Alt+` with the mouse elsewhere, a tray app that starts shows within 10 s; the grid was read as it opened.
- Rejected: WinForms' MouseEnter events (each tile is its own control and the title bar is outside the client area, so it needs hooks on each tile and the title bar); switching the timer between 2 s and 10 s (needs its own "mouse came" detection to read at once); a test-only option for a faster unused rate (the GUI test would no longer check the real rate). The GUI test now takes about 30 s instead of about 15 s, since its test icon shows and goes at the 10 s refresh.
- Decided by: the owner (Claude's suggestions; mouse only after the review), To do 8.
